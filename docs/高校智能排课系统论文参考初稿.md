## 3. 摘要初稿

高校排课工作涉及课程、教师、班级、教室和上课时间等多类资源，其本质属于带有多重约束条件的组合优化问题。传统人工排课方式存在效率低、冲突多、调整成本高等问题，难以适应教学规模扩大和排课规则复杂化的管理需求。为提高排课效率与课表质量，本文设计并实现了一套高校智能排课系统。

本系统采用前后端分离架构，后端基于 Spring Boot、Spring Security、MyBatis-Plus、MySQL 和 Redis 构建，前端基于 Vue 3、Vite、Pinia 与 Naive UI 实现，形成了教学任务管理、课表生成、课表发布、课表查询、调课处理、统计分析等功能闭环。在系统架构上，项目采用多模块 Maven 组织方式，将公共能力、排课算法、后端业务和外部适配能力进行解耦，提升了系统的可维护性与可扩展性。

在排课求解方面，系统将教学任务抽象为待调度对象，将时间槽和教室资源抽象为可分配对象，并实现了贪心算法和遗传算法两类排课策略。贪心算法用于快速生成可行课表，遗传算法用于在复杂约束条件下搜索更优排课结果。系统当前已实现教师冲突、班级冲突、教室冲突以及教室资源匹配等核心约束检查，并通过课表主表与课表明细表相结合的方式实现排课结果持久化与版本化管理。

此外，系统还支持课表异步生成、调课申请、课程交换、冲突重算和统计分析等扩展功能，使排课结果不再停留于一次性生成，而是能够在教学运行过程中持续维护。源码分析表明，该系统已具备较完整的教学任务输入、智能排课求解、课表生命周期管理和结果分析能力，能够为高校教学管理信息化与排课智能化提供工程化参考。

**关键词**：智能排课；高校教学管理；Spring Boot；Vue 3；贪心算法；遗传算法

## 4. 研究背景与问题定义

高校排课是教学管理中的核心环节。排课过程需要在有限时间内，将课程、教师、班级与教室资源映射到具体的时间槽中，并满足多种业务约束。若仅依赖人工方式，不仅工作量大，而且容易出现教师时间冲突、班级课程重叠、教室重复占用等问题。

从优化问题角度看，高校排课具有以下典型特征：

- 资源类型多，涉及教师、班级、课程、教室和校区等多类对象
- 约束条件多，既包含不可违反的硬约束，也包含希望尽量满足的软约束
- 组合空间大，任务规模扩大后搜索复杂度快速上升
- 排课结果不是静态终点，后续仍可能发生调课、交换、归档和重新发布

因此，一个可用的高校排课系统不仅需要完成基础数据管理，还需要具备自动求解、冲突检测、结果维护和数据分析等综合能力。

## 5. 系统建设目标

结合当前源码实现，系统建设目标可概括为以下几个方面：

- 建立统一的教学基础数据模型，覆盖用户、教师、学生、班级、课程、教室、院系和校区等对象
- 以教学任务作为排课输入源，支持管理员集中维护学期开课计划
- 提供自动排课能力，并支持按算法类型切换求解策略
- 实现课表版本管理、发布、归档和删除等生命周期控制
- 面向管理员、教师和学生提供分角色课表查询能力
- 提供调课申请、课程交换和冲突重算能力，支持课表动态维护
- 从课表结果中进一步提取冲突报告、教师工作量和教室利用率等统计信息
- 为未来对接正方、青果等外部教务系统预留同步适配能力

## 6. 系统总体架构设计

### 6.1 架构风格

系统采用前后端分离和多模块解耦的总体架构。前端负责页面展示、交互控制和权限路由，后端负责认证鉴权、业务处理、排课求解和数据持久化。后端内部进一步按照“公共能力层、算法层、业务层、适配层”划分模块。

### 6.2 模块划分

当前仓库主要由以下模块组成：

- `course-scheduling-common`：提供统一返回体、异常处理、JWT 工具、Redis 工具和常量定义等公共能力
- `course-scheduling-algorithm`：提供贪心算法、遗传算法、排课模型以及约束检查器接口
- `course-scheduling-admin`：作为后端主应用模块，承担认证、教学任务、课表、调课、统计和用户管理等 REST 接口
- `course-scheduling-adapter`：作为外部系统适配模块，定义同步接口并为正方、青果等系统预留扩展骨架
- `course-scheduling-web`：作为前端单页应用模块，实现桌面端与移动端统一入口
- `database/mysql`：提供数据库初始化脚本和示例数据

### 6.3 运行环境

系统运行依赖如下组件：

- Spring Boot 后端服务，默认端口 `8080`
- Vue 前端开发服务，默认端口 `3000`
- MySQL 8.0 数据库，默认端口 `3306`
- Redis 服务，默认端口 `6379`

其中，Redis 在当前实现中主要用于 JWT 退出登录后的黑名单控制，而非用户登录态的主存储介质。

## 9. 数据库设计与核心数据模型

### 9.1 数据建模思路

数据库采用“基础数据层 + 排课业务层 + 约束层 + 调课层 + 同步扩展层”的设计方式。该结构既支持日常教学资源管理，也支持排课结果存储与后续维护。

### 9.2 核心实体

系统中的关键数据对象包括：

- `sys_user`：用户表，保存账号、密码、角色、联系方式和状态
- `sys_campus`、`sys_department`：校区与院系基础组织信息
- `edu_teacher`、`edu_student`、`edu_class`：教师、学生与班级基础信息
- `edu_course`：课程信息，包括课程类型、学分、课时和资源需求
- `edu_classroom`：教室资源信息，包括容量、类型和设备属性
- `edu_teaching_task`：教学任务表，作为自动排课的直接输入
- `sch_timetable`：课表主表，记录学期、版本、状态和统计指标
- `sch_timetable_detail`：课表明细表，记录每一条已安排课程的具体时段与教室
- `adj_application`、`adj_swap_application`：调课与交换申请表
- `con_teacher_time`、`con_classroom_time`：教师和教室时间约束表
- `sync_config`、`sync_log`：外部系统同步配置和同步日志

### 9.3 数据关系

系统的数据关系可概括为：一条教学任务关联一门课程、一名教师和一个班级；课表主表可以包含多条课表明细；课表明细来源于教学任务；调课与交换流程围绕课表明细展开。该设计使得“排课输入”和“排课输出”在结构上分离，符合排课系统的业务特征。

## 10. 后端核心实现分析

### 10.1 认证与权限控制

系统采用 JWT + Spring Security 的无状态认证方案。用户登录后，后端生成包含用户身份信息的 JWT，前端在后续请求中通过请求头携带该 Token。后端过滤器解析 Token 并构建当前认证上下文。用户退出时，系统将 Token 写入 Redis 黑名单，以避免已注销 Token 被继续使用。

当前权限模型主要基于角色控制，并辅以数据范围过滤。例如，教师仅能查看本人教学任务和本人课表，学生仅能查看所在班级的课表，管理员具备全量访问权限。这种设计能满足课程设计或毕业论文层面的基础权限需求，但尚未扩展至菜单级、按钮级或更细粒度的数据权限模型。

### 10.2 教学任务管理

教学任务模块是整个系统的排课输入层。管理员可维护教学任务的学期、课程、教师、班级、周学时、总周数、优先级和状态等信息，教师则只能查看与本人相关的任务。系统在分页查询时支持按学期、状态和课程关键字进行过滤，从而为后续排课提供结构化输入数据。

### 10.3 课表生成与生命周期管理

课表生成流程由 `TimetableController`、`TimetableServiceImpl` 和 `ScheduleServiceImpl` 共同完成。系统根据学期查找当前最新课表版本，在此基础上递增版本号，然后调用排课服务完成求解，并将结果写入课表主表与课表明细表。生成后的课表初始状态为 `DRAFT`，管理员可进一步执行发布、归档和删除操作。

课表发布后，系统会将对应教学任务的状态更新为 `SCHEDULED`。若课表已归档，则不能再次发布；若课表已发布，则不能直接删除。由此可见，系统已经形成了较清晰的课表生命周期状态机。

### 10.4 异步排课实现

考虑到排课过程可能耗时较长，系统提供了异步生成接口。异步任务由线程池执行，状态信息通过 `ConcurrentHashMap` 保存在内存中，前端通过轮询接口获取任务状态并在成功后跳转到课表详情页。该实现改善了用户体验，但异步任务状态当前并未持久化，服务重启后状态会丢失，这也是后续可优化的重要方向。

### 10.5 调课与交换处理

调课模块不仅支持冲突检测，还支持申请提交、申请取消、执行调课和执行交换。执行调课或交换后，系统会对受影响时段重新标记冲突，并同步更新课表冲突总数；如果课表处于已发布状态，还会驱动相关教学任务在 `ADJUSTING` 和 `COMPLETED` 等状态间流转。这说明系统已经不只是“生成课表”，而是形成了课表运行期维护闭环。

### 10.6 统计分析模块

统计模块围绕指定课表提供总学时、课程数、教室利用率、教师工作量和冲突报告等分析结果。其作用在于将排课结果从静态明细进一步提升为可量化评估的数据对象，为论文中的“结果分析”章节提供了较好的落点。

## 11. 前端实现与交互设计

### 11.1 前端架构

前端基于 Vue 3 构建，使用 Vue Router 实现路由守卫，使用 Pinia 管理用户登录态与界面状态，并通过 Axios 拦截器在请求中自动附带 JWT。当前页面结构与后端接口有较强的一一对应关系，便于前后端协作和系统扩展。

### 11.2 多终端布局

系统通过 `ResponsiveLayout` 在窗口宽度达到阈值时切换桌面布局和移动布局，而不是仅依赖单一响应式页面压缩。这意味着系统在实现层面同时考虑了桌面端和移动端的使用体验，符合教务管理场景中“管理员偏桌面端、教师偏移动端”的实际需求。

### 11.3 角色化界面呈现

首页、课表详情页和查询页会根据管理员、教师、学生三类角色调整可见菜单、统计范围和课表视图。例如，教师在首页看到的是“我的授课安排”，学生看到的是“我的课程”，管理员看到的是学期全局课表概览。这种设计使同一套前端页面能够服务多个角色，同时减少界面重复建设成本。

## 12. 排课算法设计

### 12.1 问题建模

系统将排课问题抽象为“教学任务集合到时间槽和教室集合的映射问题”。其中，教学任务包含课程、教师、班级、周学时、优先级和资源需求等信息；教室包含容量、类型、设备和校区等属性；时间槽则由工作日和节次共同组成。

### 12.2 贪心算法设计

贪心算法的核心思路是按照任务优先级和周学时对教学任务排序，然后依次为每个任务寻找当前最优时间槽和教室。算法主要考虑以下因素：

- 教师时间是否冲突
- 班级时间是否冲突
- 教室是否已被占用
- 教室容量是否满足学生人数要求
- 教室属性是否满足课程资源需求
- 上午时段、周一至周四时段的优先加分
- 教师常驻校区与教室校区匹配加分
- 同一课程多次授课尽量分散到不同日期

贪心算法的优势是实现简单、执行速度快、便于快速生成一份可用课表；不足是更容易陷入局部最优，对全局排课质量的提升能力有限。

### 12.3 遗传算法设计

遗传算法将每个排课方案表示为染色体，将一次课程安排表示为基因，并通过种群初始化、适应度计算、选择、交叉、变异和精英保留等操作逐代搜索更优解。当前适应度函数主要由以下部分构成：

- 冲突数量惩罚
- 未完整排课任务惩罚
- 上午时段奖励
- 周一至周四奖励
- 多次课程分散到不同日期奖励
- 完整排课比例奖励

相较于贪心算法，遗传算法更适合处理复杂组合优化问题，能够在更大的解空间中进行全局搜索，但计算开销更高，参数配置也更复杂。

### 12.4 约束实现边界

当前代码中已经实际参与求解的约束，主要包括教师冲突、班级冲突、教室冲突和教室资源匹配约束。数据库中虽然已经设计了教师时间约束表、教室时间约束表，教学任务中也预留了固定星期、固定节次、固定教室和时间偏好字段，但这些扩展约束尚未完整接入当前求解主流程。

因此，论文中应准确表述为：系统已经实现了排课核心约束和双算法求解框架，但对于复杂偏好约束、固定时段约束和外部同步约束，当前仍处于预留或部分接入阶段。

## 13. 核心业务流程描述

### 13.1 登录认证流程

用户在登录页输入账号密码后，前端调用登录接口，后端校验用户身份和密码正确性，随后生成 JWT 并返回。前端将 Token 保存在本地状态中，并在后续请求中自动携带。若用户退出登录，系统会将当前 Token 写入 Redis 黑名单，从而实现注销控制。

### 13.2 自动排课流程

管理员在课表页面选择学期与算法类型后，可发起同步排课或异步排课。后端首先查询待排教学任务和可用教室，再根据请求的算法类型调用贪心算法或遗传算法完成求解。求解成功后，系统写入课表主表与课表明细表，并重新统计冲突数量和课表汇总指标。

### 13.3 课表发布流程

新生成课表默认状态为草稿。管理员确认结果后可将课表发布，系统同步将相关教学任务状态标记为已排课。若后续该版本不再继续使用，可将其归档。这样的状态管理机制有利于保证课表结果的版本可追踪性和业务一致性。

### 13.4 调课与交换流程

教师或管理员可先对目标时段进行冲突检测，检测通过后再提交调课或交换申请。申请通过或直接执行后，系统会更新课表明细、重算受影响时段冲突，并在必要时同步教学任务状态。该流程反映出系统不仅支持课表生成，也支持课表投入使用后的持续维护。

## 14. 系统特色与可提炼亮点

从论文写作角度，当前系统较值得提炼的特色包括：

- 采用多模块 Maven 架构，将公共能力、算法逻辑、业务服务和适配能力进行解耦
- 同时实现贪心算法与遗传算法，便于进行算法对比分析
- 采用课表主表与课表明细表组合方式，支持课表版本化管理
- 支持异步排课生成，提升长耗时任务下的交互体验
- 支持调课与课程交换，形成课表动态维护闭环
- 支持按角色过滤课表视图，兼顾管理员、教师与学生三类使用场景
- 支持多终端布局切换，增强系统可用性

## 15. 当前系统的局限性

虽然系统主体已经较完整，但从源码看仍存在一些明显局限：

- 复杂约束尚未完全进入排课求解主流程，尤其是固定时段、教师不可用时段和时间偏好等字段仍偏预留设计
- 异步排课任务状态保存在内存中，缺少 Redis 或数据库持久化机制
- 统计模块中的总学时和教室总时段采用简化计算方式，与真实教学周次和节次利用率仍有差距
- 外部教务系统适配模块当前主要是接口与骨架实现，尚未形成真实同步闭环
- 自动化测试已覆盖认证、权限过滤、部分控制器与调课服务，但整体测试面仍然有限，算法正确性和性能回归测试仍可加强

这些不足既说明系统还有继续完善空间，也为论文结尾部分的“系统不足与展望”提供了真实依据。
