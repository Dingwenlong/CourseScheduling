# 高校智能排课系统论文正文扩展稿

## 摘要

高校课程排课是教学管理中的关键环节，其核心任务是将课程、教师、班级、教室与时间资源进行合理匹配。由于排课过程同时受到教师时间、班级安排、教室容量、教室类型以及教学计划等多类约束影响，传统依赖人工经验的排课方式普遍存在效率低、冲突多、调整困难等问题。随着高校教学规模扩大和教学组织复杂度提升，构建一套具备自动排课、冲突检测、课表维护和统计分析能力的智能排课系统具有较强的现实意义。

本文设计并实现了一套高校智能排课系统。系统采用前后端分离架构，后端基于 Spring Boot、Spring Security、MyBatis-Plus、MySQL 与 Redis 构建，前端基于 Vue 3、Vite、Pinia 与 Naive UI 实现。在工程结构上，系统通过多模块 Maven 方式将公共能力、排课算法、业务服务和扩展适配模块进行解耦，从而提升了系统的可维护性与扩展性。

在功能设计方面，系统围绕教学任务维护、课表生成、课表发布、课表查询、调课处理、课程交换和统计分析等业务展开，实现了从排课输入到排课结果维护的完整闭环。在算法设计方面，系统将排课问题抽象为教学任务到时间槽和教室资源的映射问题，分别实现了贪心算法和遗传算法两类排课策略。其中，贪心算法用于快速生成可行课表，遗传算法用于在更复杂的约束空间中搜索更优结果。系统当前已实现教师冲突、班级冲突、教室冲突和教室资源匹配等核心约束处理，并通过课表主表与课表明细表实现排课结果的版本化存储。

实践结果表明，该系统能够完成高校教学场景下的基础排课与课表维护任务，并具备较好的工程可扩展性。从论文研究角度看，本文工作不仅实现了教学管理信息化，也为后续开展复杂约束接入、算法性能优化和排课效果评估提供了系统基础。

**关键词**：高校排课；智能排课系统；Spring Boot；Vue 3；贪心算法；遗传算法

## Abstract

Course scheduling is a core task in university teaching administration. Its goal is to assign courses, teachers, classes, classrooms, and time resources in a coordinated manner. Since the scheduling process is constrained by teacher availability, class timetables, classroom capacity, classroom type, and teaching plans, traditional manual scheduling methods often suffer from low efficiency, frequent conflicts, and high adjustment costs. With the increasing scale and complexity of higher education management, it is of practical significance to design and implement an intelligent course scheduling system.

This paper designs and implements an intelligent course scheduling system for universities. The system adopts a front-end and back-end separated architecture. The back end is developed with Spring Boot, Spring Security, MyBatis-Plus, MySQL, and Redis, while the front end is developed with Vue 3, Vite, Pinia, and Naive UI. In terms of engineering structure, the project uses a multi-module Maven architecture to decouple common utilities, scheduling algorithms, business services, and extension adapters, thereby improving maintainability and scalability.

Functionally, the system covers teaching task management, timetable generation, timetable publishing, timetable query, course adjustment, course exchange, and statistical analysis, forming a complete closed loop from scheduling input to result maintenance. In algorithm design, the scheduling problem is modeled as a mapping from teaching tasks to time slots and classroom resources. Two scheduling strategies, namely a greedy algorithm and a genetic algorithm, are implemented. The greedy algorithm is used for quickly generating feasible timetables, while the genetic algorithm is used for searching better solutions under more complex constraints. The current implementation supports core constraints such as teacher conflicts, class conflicts, classroom conflicts, and classroom-resource matching, and stores scheduling results in a versioned structure through timetable master and detail tables.

The implementation shows that the system can support basic university scheduling and timetable maintenance scenarios with good extensibility. From a research perspective, this work not only realizes teaching administration informatization, but also provides a practical basis for further studies on complex constraint integration, algorithm optimization, and scheduling quality evaluation.

**Key Words**: university course scheduling; intelligent scheduling system; Spring Boot; Vue 3; greedy algorithm; genetic algorithm

## 第一章 绪论

### 1.1 研究背景

高校教学活动的组织依赖于稳定而合理的课程安排。排课工作表面上是时间分配问题，实质上是教学资源的综合协调问题。在一个完整的排课过程中，管理人员需要同时考虑课程性质、教师安排、班级人数、教室容量、教室类型以及校区分布等多方面因素。如果仅依赖人工经验排课，不仅工作量大，而且容易在排课结果中产生教师时间冲突、班级课程重叠、教室资源重复占用等问题。

随着高校信息化建设不断推进，教学管理工作对系统化、规范化和智能化提出了更高要求。尤其在多学院、多班级、多教室并行组织教学的场景下，传统排课方式已难以适应高频迭代和动态调整的管理需求。因此，研究并实现一套面向高校场景的智能排课系统，具有明显的现实需求和应用价值。

从计算问题角度看，课程排课具有典型的多约束组合优化特征。排课结果既要满足硬约束，如教师、班级和教室在同一时间不能重复占用，也要尽可能满足软约束，如课程时段偏好、课程分散度和资源利用率等。由于可行解空间庞大，该问题通常被视作复杂优化问题。因此，排课系统不仅是一个教学管理信息系统，也是一类包含优化求解能力的智能应用系统。

### 1.2 研究意义

本课题的研究意义主要体现在以下两个方面。

首先，在实际应用层面，智能排课系统能够将原本依赖人工经验的大量重复性工作交由系统处理，从而提高教学管理效率，降低排课冲突率，减少人工调整成本。同时，系统通过课表发布、课表查询、调课申请和统计分析等功能，能够支撑教学运行过程中的持续维护，提高教学组织的规范性和透明度。

其次，在研究与工程实践层面，高校排课问题兼具信息系统设计和智能优化算法研究双重特征。一方面，系统需要具备较完整的数据模型、权限控制、业务流程和前后端协同能力；另一方面，系统又需要通过合理的问题建模和算法设计来提高排课结果质量。因此，该课题适合作为“管理信息系统 + 智能优化算法”结合型研究对象，具有较强的课程设计和毕业论文研究价值。

### 1.3 国内外研究现状

从国内外研究情况看，课程排课问题长期以来一直是教育信息化和优化计算领域的重要研究方向。国外相关研究较早地将课程排课归入组合优化问题，并广泛采用启发式算法、遗传算法、模拟退火、禁忌搜索和混合优化算法等方法求解。部分研究还将排课质量与资源利用率、教师满意度和课程分布均衡性结合起来进行综合评价。

国内高校在排课系统建设方面多以教务管理平台为依托，重点解决课程安排、教师调度和教室使用等实际业务问题。近年来，随着人工智能和智能优化方法的引入，越来越多研究开始关注利用遗传算法、粒子群算法和约束满足方法来提升自动排课质量。然而，从实际落地情况看，很多系统要么偏重后台管理与信息录入，算法能力不足；要么偏重算法仿真验证，业务闭环不完整。因而，将完整业务流程与可实际运行的排课算法结合起来，仍然具有现实研究意义。

### 1.4 本文研究内容

本文围绕高校排课场景，完成了一个智能排课系统的设计与实现，主要研究内容包括以下几个方面：

- 建立教学基础数据、教学任务、课表结果、调课申请和统计分析等核心数据模型
- 实现教学任务管理、自动排课、课表发布、课表查询、调课交换和统计分析等主要功能
- 对排课问题进行抽象建模，分别设计并实现贪心算法和遗传算法
- 对系统当前实现效果、技术特点和存在局限进行总结，并提出后续优化方向

## 第二章 需求分析

### 2.1 系统建设目标分析

高校智能排课系统的建设目标不是单纯生成一张课表，而是围绕教学任务形成完整的排课管理闭环。结合当前系统源码与业务结构，系统建设目标可概括为：以教学任务为输入，以自动排课和课表版本管理为核心，以调课维护和统计分析为支撑，构建一套面向高校日常教学管理场景的综合应用系统。

从业务角度看，系统需要解决以下几类问题：

- 如何统一维护课程、教师、班级和教室等基础数据
- 如何以结构化方式维护某一学期的教学任务
- 如何自动生成满足核心约束的课表结果
- 如何在课表发布后继续处理冲突、调课和交换问题
- 如何向不同角色提供适配的查询与统计结果

### 2.2 用户角色需求分析

#### 2.2.1 管理员需求

管理员是系统中的核心管理角色，主要负责教学数据维护和课表管理。其核心需求包括：

- 维护教学任务，包括新增、修改、删除和查询任务
- 选择学期和算法类型，发起自动排课
- 查看不同版本课表的详情、冲突和统计信息
- 对课表执行发布、归档和删除等生命周期操作
- 处理调课和交换带来的课表更新问题
- 管理系统用户和重置用户密码

#### 2.2.2 教师需求

教师角色主要关心与本人授课相关的教学安排。其核心需求包括：

- 查看本人所承担的教学任务
- 查询本人在某学期的授课课表
- 对已有课表进行调课冲突检测
- 提交调课申请或课程交换申请
- 查看申请执行结果以及调整后的最新课表

#### 2.2.3 学生需求

学生角色当前在系统中的权限相对简单，主要聚焦于课表查看。其核心需求包括：

- 查看本人所属班级在当前学期的课表安排
- 查看课程明细、任课教师、上课教室和上课时间
- 通过界面快速了解当前班级的排课结果

### 2.3 功能需求分析

根据源码中控制器、服务层和前端页面实现，系统功能需求可划分为以下几个模块。

#### 2.3.1 用户认证与权限控制

系统需要支持用户登录、退出、获取当前用户信息、修改密码和管理员重置密码。系统需要根据不同用户角色对接口和数据范围进行限制，保证教师只能访问与本人相关的数据，学生只能访问与本人班级相关的数据，管理员可以访问全局数据。

#### 2.3.2 教学任务管理

教学任务是自动排课的数据来源，因此系统需要支持按学期维护教学任务信息，包括课程、教师、班级、周学时、总周数、优先级、课程性质等字段，并支持分页查询与关键字检索功能。

#### 2.3.3 自动排课管理

系统需要支持按学期和算法类型生成课表，并能区分同步生成与异步生成两种模式。生成后的课表应具备版本号、状态、冲突数、已排课数量和利用率等汇总信息，以便后续继续管理。

#### 2.3.4 课表查询与展示

系统需要支持管理员查看完整课表，也需要支持教师查看本人授课课表、学生查看本班课表。查询结果不仅要支持列表化展示，还应支持按周视图展示课程安排，以便用户更直观地理解课表结构。

#### 2.3.5 调课与交换处理

系统需要支持对既有课表进行动态维护。具体包括：

- 对目标调课时段进行冲突检测
- 提交调课申请并保存申请状态
- 执行调课后更新课表明细
- 支持两门课程之间的课程交换
- 在执行后重新统计冲突并更新相关教学任务状态

#### 2.3.6 统计分析

系统需要对课表结果进行进一步量化分析，包括：

- 统计总学时和课程数量
- 统计不同教室的时段利用率
- 统计教师工作量和平均课程负载
- 形成冲突报告并展示冲突详情

### 2.4 非功能需求分析

除功能需求外，系统还应满足一定的非功能需求。

#### 2.4.1 可用性需求

系统应提供清晰的界面导航和角色化页面展示，确保管理员、教师和学生都能快速进入与自己相关的功能模块。同时，前端应支持桌面端和移动端两类布局，以适应不同使用终端。

#### 2.4.2 安全性需求

系统应实现基础身份认证与权限控制，保证不同角色只能访问被授权的业务数据。对于登录状态失效、无权限访问和非法请求等情况，系统应返回统一且明确的错误信息。

#### 2.4.3 可维护性需求

系统结构需要尽量解耦，以便后续维护和扩展。当前项目通过多模块 Maven 结构，将公共能力、算法实现、业务服务和适配能力分离，符合较好的可维护性要求。

#### 2.4.4 可扩展性需求

排课业务在真实场景中常常需要扩展新的约束条件、统计指标和外部系统接口，因此系统应保留扩展空间。当前数据库中已经预留了教师时间约束表、教室时间约束表和外部系统同步表，说明系统在设计阶段已考虑后续扩展需求。

#### 2.4.5 性能需求

自动排课属于相对耗时的处理过程，因此系统需要避免在长时间计算中阻塞用户操作。当前系统通过异步排课与前端轮询相结合的方式，在一定程度上满足了长耗时任务场景下的性能体验要求。

### 2.5 业务流程分析

#### 2.5.1 教学任务到课表生成流程

管理员首先维护某学期的教学任务，系统将这些任务作为排课输入。随后管理员选择算法类型发起自动排课，系统加载教学任务和可用教室信息后执行求解，最终生成课表主表和课表明细，并将结果持久化。

#### 2.5.2 课表生命周期流程

新生成的课表初始状态为草稿。管理员可对草稿课表进行查看和校验；确认无误后将其发布；若该版本后续不再继续使用，则可归档。系统通过课表状态控制，保证课表管理具有明确的生命周期边界。

#### 2.5.3 调课维护流程

当教师或管理员发现既有课表安排需要调整时，系统首先对新时段进行冲突检查；若检查通过，则允许提交调课申请或直接执行调课。调课完成后，系统会重新标记受影响课程的冲突状态，并同步更新课表和教学任务相关信息。

### 2.6 本章小结

本章从系统建设目标、用户角色、功能需求、非功能需求和业务流程等方面对高校智能排课系统进行了分析。需求分析结果表明，排课系统不仅需要完成基础教学数据管理和课表生成，还需要在课表发布后继续支持动态维护和统计分析。因此，系统设计必须同时覆盖业务闭环、算法求解、权限控制和前后端协同等多个层面，为后续总体设计和详细实现提供依据。

## 第三章 系统总体设计

### 3.1 总体架构设计

本系统采用前后端分离架构。前端负责页面展示、交互逻辑和路由控制，后端负责认证授权、业务处理、排课求解和数据持久化。数据库用于存储用户信息、教学任务、课表结果和申请记录，Redis 用于处理注销 Token 黑名单等缓存型数据。

从模块协同关系看，系统的总体架构可以概括为四层：

- 表现层：由 Vue 3 前端页面组成，负责用户交互和结果展示
- 业务层：由 Spring Boot 后端接口和业务服务组成，负责业务编排
- 算法层：由独立算法模块组成，负责排课求解逻辑
- 数据层：由 MySQL 和 Redis 组成，负责持久化和辅助缓存

### 3.2 后端模块设计

后端采用多模块 Maven 方式组织，主要包括以下模块：

#### 3.2.1 公共模块

公共模块封装统一返回结构、结果码、异常处理、JWT 工具、Redis 工具以及系统常量，供其他业务模块复用。该模块的存在减少了重复代码，并保证接口风格和异常处理机制的一致性。

#### 3.2.2 算法模块

算法模块独立于业务模块之外，主要负责排课问题建模和求解。模块中定义了任务数据模型、教室数据模型、时间槽模型、排课结果模型，以及贪心算法和遗传算法两类调度器。该模块化设计有助于后续替换算法或补充新的优化策略。

#### 3.2.3 管理端业务模块

管理端模块是系统后端的核心应用模块，包含认证管理、教学任务管理、课表管理、调课管理、统计分析和用户管理等控制器与服务。该模块直接对外提供 REST 接口，并负责业务流程编排和数据库交互。

#### 3.2.4 适配扩展模块

适配模块当前主要定义了外部同步接口及针对不同教务系统的同步器骨架，如正方和青果系统同步器。该模块尚未形成完整业务闭环，但为后续系统扩展提供了接口基础。

### 3.3 前端模块设计

前端采用 Vue 3 单页应用架构，主要包括以下部分：

- 路由模块：负责页面导航、登录守卫和角色访问控制
- 状态管理模块：负责保存用户信息、主题状态和布局状态
- 请求模块：负责统一处理 Axios 请求头、异常响应和登录失效跳转
- 布局模块：负责桌面端与移动端页面切换
- 页面模块：负责首页、任务页、课表页、调课页、统计页和个人中心等具体业务交互

### 3.4 数据库总体设计

数据库从业务层面可分为五类数据：

- 系统管理数据：如用户、院系、校区
- 教学基础数据：如课程、班级、教师、学生、教室
- 排课业务数据：如教学任务、课表主表、课表明细
- 调课申请数据：如调课申请表和交换申请表
- 扩展与约束数据：如教师时间约束、教室时间约束、同步配置和同步日志

这种分层设计能够较清晰地表达不同类型数据之间的职责边界，也有利于在论文中单独展开数据库设计部分。

### 3.5 关键设计思路

#### 3.5.1 输入输出分离设计

系统将教学任务作为排课输入，将课表主表和课表明细作为排课输出，实现了输入层与结果层的结构化分离。这样的设计有利于重复生成多个版本课表，也便于对历史版本进行管理和比较。

#### 3.5.2 版本化课表设计

系统按照学期和版本号维护课表，同一学期可以存在多个版本。管理员可以在不同版本之间切换查看，并通过发布和归档操作控制最终生效的课表结果。这种设计能够较好地适应多轮试排和结果修正场景。

#### 3.5.3 异步排课设计

自动排课可能耗时较长，因此系统支持异步生成模式。该设计将排课任务放入线程池执行，并通过任务状态接口供前端轮询获取结果，降低了用户在等待排课过程中的阻塞感。

#### 3.5.4 多角色数据过滤设计

系统不仅在接口层进行角色权限控制，还在数据结果层根据管理员、教师和学生角色进行过滤。例如，教师仅能看到与本人相关的课表明细，学生仅能看到本班课表。这样既保证了安全性，也增强了不同角色下界面的针对性。

### 3.6 本章小结

本章对系统总体架构、后端模块、前端模块、数据库结构和关键设计思路进行了说明。总体来看，系统在工程结构上采用了较清晰的模块化组织方式，在业务结构上形成了从教学任务输入到课表维护输出的完整闭环，并为后续算法设计与功能实现奠定了基础。

## 第四章 系统关键功能实现

### 4.1 用户认证模块实现

用户认证模块是系统安全控制的基础。当前系统采用 JWT 与 Spring Security 相结合的无状态认证机制。用户在登录页输入用户名和密码后，前端调用登录接口，将登录信息发送到后端。后端首先根据用户名查询用户记录，再校验密码是否正确以及账号状态是否可用。只有当用户名、密码和状态全部满足要求时，系统才会生成 Token 并返回给前端。

在前端实现中，Axios 请求拦截器会自动将 Token 加入 `Authorization` 请求头。后端在请求进入业务接口前，通过 JWT 认证过滤器解析 Token，并对用户 ID、用户名、角色和状态进行校验。如果发现用户已禁用、角色已变化或 Token 已失效，则直接终止请求并返回统一错误码。该设计保证了系统认证链路的完整性，也降低了后端会话维护成本。

在注销逻辑上，系统并未采用传统 Session 失效方式，而是将已注销的 Token 写入 Redis 黑名单，并在后续请求中判断该 Token 是否已被作废。该方案与 JWT 无状态认证机制相匹配，适合当前系统的轻量化部署场景。

### 4.2 教学任务管理模块实现

教学任务管理模块是排课系统的输入端。管理员可通过任务管理页面维护学期教学任务，系统支持分页查询、新增、修改和删除操作。任务数据主要包括学期、课程、教师、班级、学生人数、周学时、总周数、上课周次、课程性质和优先级等字段。

在后端实现中，教学任务查询支持按学期、状态和关键字过滤。若当前登录用户为教师，系统会自动按照教师身份过滤结果，仅返回与本人相关的教学任务数据。这种“接口权限 + 数据范围”双重控制方式，使同一接口在多角色场景下仍能保持较好的通用性。

从业务意义上看，教学任务表承担的是“开课计划”角色，它既不是静态课程目录，也不是最终课表，而是排课算法的直接输入源。通过将教学任务独立建模，系统实现了业务输入层与排课结果层的分离。

### 4.3 自动排课模块实现

自动排课模块是系统的核心功能。管理员在前端选择学期、算法类型和相关参数后，可发起同步生成或异步生成请求。后端首先读取指定学期内状态为待排课的教学任务，再读取当前可用教室资源，并将二者转换为算法模块所需的标准化输入对象。

在同步排课模式下，后端直接调用课表生成服务完成排课并返回结果；在异步模式下，系统会先创建一个任务状态对象，然后将排课任务提交至线程池执行，前端则通过轮询接口持续获取任务状态。任务执行完成后，系统返回生成成功或失败信息以及对应课表 ID。

课表生成成功后，系统会执行以下处理：

- 根据学期查找当前最新课表版本，并自动生成新版本号
- 将排课参数封装后写入课表主表
- 将算法输出逐条转换为课表明细写入数据库
- 对已生成课表进行冲突重标记
- 更新冲突总数、已排课数量和利用率等汇总信息

该模块实现表明，系统已经将“算法求解”与“业务落库”连接成一条完整链路，而不只是停留在算法仿真阶段。

### 4.4 课表查询与生命周期管理实现

课表管理模块围绕课表主表与课表明细展开。系统支持分页查询课表版本、根据 ID 查看课表、获取课表明细、查看冲突记录以及按班级、教师、教室三个维度查询课表。

在生命周期控制方面，课表状态分为草稿、已发布和已归档三类。系统规定：新生成课表默认为草稿；管理员确认结果后可发布；归档后的课表不再用于继续发布；已发布课表不能直接删除，必须先归档。与此同时，课表发布还会触发相关教学任务状态从待排课向已排课状态切换。这样的设计确保了课表版本管理具备明确的业务语义。

前端在课表详情页中采用“统计卡片 + 周视图 + 列表视图 + 冲突视图”的组织方式，使用户既能从宏观层面查看课表概况，又能从明细层面查看每门课程的时间、教师、班级和教室信息。对于教师和学生角色，页面会根据当前身份自动过滤课表范围，实现差异化展示。

### 4.5 调课与交换模块实现

调课与交换模块反映了系统在课表运行期维护方面的能力。当前系统支持单门课程调课和两门课程交换两种模式。两种模式在业务处理上都遵循“先检测，再申请，再执行，再重算”的基本思路。

在调课流程中，系统首先根据目标星期、目标节次和目标教室构造预览结果，然后对目标时段中的教师、班级和教室冲突进行检查。若无冲突，则允许用户提交申请或直接执行；执行成功后，系统更新课表明细，并重新标记受影响时段的冲突信息，同时更新课表的冲突总数。

在交换流程中，系统会对两门课程交换后的新位置分别进行冲突检查。若两边都满足要求，则执行时间与教室字段互换，并在执行后关闭相关待处理申请。若课表已经发布，系统还会同步驱动相关教学任务状态在调课中和已完成之间流转。由此可见，该模块不仅实现了课程位置变更，还兼顾了冲突一致性和业务状态一致性。

### 4.6 统计分析模块实现

统计分析模块的目标是将课表结果从“可查看”提升为“可评估”。系统围绕指定课表提供四类统计输出：

- 总学时与课程数量
- 教室利用率
- 教师工作量
- 冲突报告

其中，教室利用率通过统计课表明细中各教室已使用时段数与总时段数得到；教师工作量通过汇总每位教师承担课程的课时与课程数得到；冲突报告则将课表明细中标记为冲突的数据进一步分类为教师冲突、班级冲突和教室冲突。虽然当前统计实现仍采用了简化计算方式，但已经具备支持排课结果横向比较和后续实验分析的基础。

### 4.7 本章小结

本章围绕认证、教学任务、自动排课、课表管理、调课维护和统计分析六个方面，对系统关键功能实现进行了说明。可以看出，当前系统并非单一的排课算法演示项目，而是已经形成了较完整的业务系统闭环，为后续算法设计分析和测试评估提供了具体载体。

## 第五章 排课算法设计与实现

### 5.1 排课问题建模

从本系统的实现来看，排课问题可抽象为：在给定教学任务集合、教室资源集合和时间槽集合的条件下，为每一项教学任务分配合适的时间和教室，使结果尽可能满足约束条件并提升排课质量。

系统中的主要模型对象包括：

- `TaskData`：表示待排教学任务，包含课程、教师、班级、周学时、优先级和资源需求等信息
- `ClassroomData`：表示教室资源，包含容量、类型、设备属性和校区信息
- `TimeSlot`：表示一个可分配的上课时段，由星期和节次组成
- `ScheduledTask`：表示最终排课结果中的一条课程安排

该建模方式的优点在于：一方面能够屏蔽底层数据库实体的复杂性，另一方面又保留了算法求解所需的关键属性，便于在业务层与算法层之间建立清晰接口。

### 5.2 约束条件设计

课程排课需要同时处理硬约束与软约束。

硬约束是必须满足的条件，当前系统已经实际实现的主要包括：

- 同一教师在同一时间不能安排多门课程
- 同一班级在同一时间不能安排多门课程
- 同一教室在同一时间不能被重复占用
- 教室容量应满足课程的学生人数需求
- 教室类型和资源属性应满足课程需求

软约束是希望尽量满足的优化目标，当前算法实现中主要体现为：

- 优先安排上午时段
- 优先安排周一至周四时段
- 优先匹配教师常驻校区和上课校区
- 优先选择容量与学生人数更接近的教室
- 尽量将同一课程的多次授课分散到不同日期

此外，数据库中已经预留了教师时间约束、教室时间约束、固定时段和时间偏好等信息，但这些约束尚未完整进入当前排课主流程。因此，论文中应将其表述为“扩展能力已预留，但尚未全部落地”。

### 5.3 贪心算法实现

贪心算法模块的基本流程如下：

1. 对待排教学任务按照优先级和周学时进行排序
2. 针对每一项任务，筛选满足条件的候选教室
3. 遍历所有可选时间槽和候选教室
4. 过滤教师冲突、班级冲突和教室冲突
5. 对候选方案进行评分，选取当前得分最高的方案
6. 将选中的时间槽和教室写入已占用资源表

在评分函数设计上，系统对上午时段、周一至周四时段、校区匹配和容量适配进行了奖励，对同一课程多次授课集中在同一天的情况进行了惩罚。由此，贪心算法能够在较短时间内快速构造出一份满足核心约束的可行课表。

贪心算法的优点在于计算速度快、实现逻辑清晰、工程实现成本低，适合作为系统的默认快速排课策略；不足在于它在每一步都只追求当前局部最优，因此面对更复杂的组合空间时，较难保证整体排课质量。

### 5.4 遗传算法实现

遗传算法模块将排课方案视作一个种群中的个体，将单次课程安排视作基因，从而通过进化方式不断搜索更优解。其实现流程如下：

1. 根据教学任务数量和周学时初始化种群
2. 为每个任务随机生成若干时间槽和教室组合，形成初始染色体
3. 统计冲突数量和未完整排课任务数量，并据此计算适应度
4. 通过锦标赛选择方式选出父代个体
5. 对父代执行交叉操作，生成新的子代个体
6. 对子代执行时间槽变异、教室变异或联合变异
7. 保留部分精英个体，并迭代进入下一代
8. 当达到目标适应度、最大代数或连续多代无显著改进时终止

当前遗传算法的适应度函数主要由三部分构成：

- 冲突惩罚项
- 未完整排课任务惩罚项
- 软约束奖励项

这种设计使算法既关注结果是否可行，也关注排课结果是否更合理。相比贪心算法，遗传算法更适合在复杂搜索空间中寻找更高质量解，但其运行时间和参数调整成本也更高。

### 5.5 两类算法的比较分析

从当前系统实现看，贪心算法和遗传算法并不是互相替代关系，而是面向不同需求场景的两类策略。

贪心算法适用于以下场景：

- 教学任务规模适中
- 对排课耗时较敏感
- 需要快速生成一份可行初稿

遗传算法适用于以下场景：

- 教学任务规模较大
- 冲突组合更复杂
- 对排课质量要求更高
- 需要进行算法对比实验

在工程实现上，系统通过统一的调度接口和统一的 `SchedulingResult` 输出对象，将两类算法封装在同一套业务流程下。这样既降低了业务层对具体算法实现的耦合，也为论文中的算法对比研究提供了便利。

### 5.6 算法实现的不足与优化方向

尽管当前算法模块已具备基本可用性，但仍存在若干可以继续优化的方向：

- 复杂约束尚未全部纳入求解过程
- 当前遗传算法适应度设计仍相对简化
- 贪心算法缺少更强的回溯与重排机制
- 未引入更精细的多目标优化指标，如教师满意度和课程均衡度
- 未对不同任务规模下的算法耗时和冲突数量进行系统化实验对比

这些不足为后续章节中的测试分析和总结展望提供了进一步讨论空间。

### 5.7 本章小结

本章对排课问题进行了建模，并分别说明了贪心算法和遗传算法在本系统中的实现方式。总体来看，系统已经具备“问题抽象清晰、核心约束可处理、双算法可切换”的基本特征。这一设计既满足当前业务需要，也为后续进一步开展算法优化研究提供了结构基础。

由于当前仓库中已存在部分单元测试和控制器测试，但未形成完整的自动化性能实验报告，因此本章更适合写成“测试设计与现有验证情况分析”，而不应写成已经完成大规模性能实测的结论式章节。

### 6.2 测试环境说明

结合当前项目配置，系统测试环境可描述为：

- 后端运行环境：Java 17、Spring Boot 3.1.10
- 前端运行环境：Node.js 18+、Vue 3、Vite 5

当前项目中已存在若干测试类，主要覆盖认证过滤、权限校验和部分调课权限边界，但尚未形成完整的端到端自动化测试体系。

### 6.3 认证与权限测试分析

从现有测试代码看，认证与权限控制是当前测试覆盖最明确的部分。系统已针对以下场景编写了测试：

- Token 对应用户已被禁用时，请求应被拒绝
- 用户登录后若角色发生变化，原 Token 应视为无效
- Token 合法且用户状态正常时，应正确建立认证上下文
- 学生访问其他班级课表时，应返回无权限结果
- 教师访问其他教师教学任务或课程明细时，应返回无权限结果

这些测试表明，系统在“认证合法性”和“数据访问边界”两个层面已有较明确的保护机制。对于毕业论文而言，这些测试能够支撑“系统具备基础安全控制能力”的结论。

### 6.4 调课与业务一致性测试分析

在调课模块方面，现有测试主要覆盖教师越权访问他人课程明细的场景，能够证明调课模块在进入业务处理前会先进行权限校验。从实现逻辑看，调课和交换在执行后还会触发冲突重算、课表冲突总数更新以及教学任务状态联动，这些都是系统保证业务一致性的关键环节。

尽管当前测试对这些复杂状态联动尚未做到全链路覆盖，但从源码实现可看出系统已经具备必要的处理逻辑。因此，在论文中可以表述为：系统已在关键权限边界上建立自动化验证基础，但在复杂状态流转和多场景组合测试方面仍有加强空间。

## 第七章 总结与展望

### 7.1 全文总结

本文围绕高校教学管理中的课程排课问题，设计并实现了一套高校智能排课系统。系统以教学任务为排课输入，以课表主表和课表明细为排课输出，构建了从任务管理、自动排课、课表发布、课表查询，到调课维护和统计分析的完整业务闭环。

在系统设计方面，本文采用前后端分离和多模块解耦架构，实现了公共能力、算法模块、业务服务和扩展适配模块之间的职责分离。在功能实现方面，系统完成了用户认证、教学任务管理、课表生成、课表生命周期管理、调课与交换处理以及统计分析等核心模块，能够较好支撑高校教学排课的基本业务需求。

在算法设计方面，本文针对高校排课问题实现了贪心算法与遗传算法两种策略。贪心算法具有实现简单、运行速度快的特点，适合快速生成可行课表；遗传算法具有较强的全局搜索能力，适合在复杂约束环境下搜索更优解。通过将两类算法纳入同一工程系统，本文实现了排课业务与优化算法的有机结合。

从当前实现结果看，该系统已经具备较强的论文可写性和工程参考价值。一方面，它不是孤立的算法实验，而是具备角色权限、业务流程和结果维护能力的完整系统；另一方面，它又保留了约束扩展、算法优化和实验对比的研究空间。

### 7.2 存在的不足

尽管系统已经完成了核心功能，但仍然存在以下不足：

- 教师不可用时间、教室不可用时间、固定时段和复杂偏好等约束尚未全部接入排课求解主流程
- 异步排课任务状态当前保存在内存中，服务重启后无法继续追踪任务
- 统计模块中部分指标采用了简化计算方式，与真实教学业务的精细化需求仍有差距
- 外部教务系统同步模块当前仍以接口和骨架实现为主，尚未完成真实对接
- 自动化测试覆盖范围有限，尚缺少大规模排课实验数据与性能测试结果

这些不足说明系统仍处于可继续深化和扩展的阶段，也为后续研究提供了明确方向。

### 7.3 未来展望

面向后续优化，系统可从以下几个方面继续改进：

- 将教师时间约束、教室时间约束和固定时段约束统一纳入求解流程
- 优化遗传算法适应度函数，引入更多反映教学质量的评价指标
- 为贪心算法增加更强的局部回溯和重排策略
- 将异步任务状态持久化到 Redis 或数据库中，提高任务管理可靠性
- 完善端到端自动化测试和算法对比实验，形成更完整的数据支撑
- 对接真实教务平台，实现基础数据自动同步

总体而言，高校智能排课系统既具有明确的现实应用价值，也具有持续优化的研究空间。随着约束建模、算法优化和系统集成能力的进一步增强，该系统能够在教学管理信息化建设中发挥更大作用。
