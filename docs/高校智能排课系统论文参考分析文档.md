## 2. 系统概述

### 2.1 建设背景

高校排课属于典型的多约束组合优化问题。教学管理部门需要在有限时间内，将课程、教师、班级、教室和学期安排映射到具体的上课时段。该过程既受到硬约束影响，也受到软约束影响。

硬约束主要包括：

- 同一教师同一时间不能出现在两门课中
- 同一班级同一时间不能安排多门课程
- 同一教室同一时间不能重复占用
- 教室容量和教室类型需要满足课程需求

软约束主要包括：

- 尽量优先安排上午或工作日前段时段
- 尽量使同一课程的多次授课分散到不同日期
- 尽量匹配教师常驻校区与上课校区
- 尽量提高教室资源利用率和整体排课满意度

因此，排课系统不仅是信息管理系统，也是一个包含优化算法、业务规则引擎和过程管理能力的综合型教学管理系统。

### 2.2 系统目标

从当前代码实现看，本系统的目标可以概括为以下几点：

- 建立统一的教学任务、课程、班级、教师、教室等基础数据模型
- 为管理员提供教学任务维护、课表生成、课表发布、冲突查看和统计分析能力
- 为教师和管理员提供调课与课程交换能力
- 支持基于不同算法策略的自动排课
- 提供桌面端和移动端自适应的统一前端界面
- 为未来与外部教务系统的数据同步预留扩展接口

### 2.3 用户角色

系统代码中定义了三类角色：

- `ADMIN`：管理员，拥有课表生成、发布、归档、用户管理、教学任务维护等完整权限
- `TEACHER`：教师，可查询任务、查看课表、提交或执行本人可管理的调课和交换申请
- `STUDENT`：学生，当前后端角色模型已具备，但前端功能主要围绕管理员与教师展开

### 2.4 核心业务功能

结合控制器和页面代码，系统当前已实现的核心业务功能包括：

- 用户登录、退出、查看个人信息、修改密码
- 教学任务分页查询、新增、修改、删除
- 课表生成、异步生成、版本管理、发布、归档、删除
- 课表详情查看、冲突记录查看
- 按班级、教师、教室查询已发布课表
- 调课冲突检测、调课申请、调课执行
- 课程交换检测、交换申请、交换执行
- 教室利用率、教师工作量、冲突报告、总学时与课程数统计

## 3. 总体架构分析

### 3.1 架构风格

系统整体采用“前后端分离 + 多模块 Maven + 独立算法引擎”的架构风格。

后端采用分层式设计：

- Controller 层负责接口暴露和参数校验
- Service 层负责业务编排
- Mapper 层负责数据库访问
- Entity/DTO/VO 负责数据承载
- Algorithm 模块负责排课核心算法
- Common 模块提供结果封装、异常处理、JWT、Redis 等公共能力

前端采用 Vue 3 单页应用架构：

- Router 负责页面导航与鉴权跳转
- Pinia 负责登录态、主题态和布局态管理
- API 层负责 Axios 请求封装
- Views 负责页面级业务交互
- Layout 负责桌面端与移动端适配

### 3.2 模块划分

当前仓库主要包含以下模块：

- `course-scheduling-common`
  - 公共基础模块
  - 提供统一返回体、异常处理、JWT 工具、Redis 工具、常量定义
- `course-scheduling-algorithm`
  - 排课算法模块
  - 提供贪心算法、遗传算法、约束检查接口与排课模型对象
- `course-scheduling-adapter`
  - 外部系统适配模块
  - 为正方、青果等教务系统同步预留接口与适配器骨架
- `course-scheduling-admin`
  - 后端主应用模块
  - 提供认证、任务、课表、调课、统计、用户等 REST API
- `course-scheduling-web`
  - Vue 3 前端模块
  - 提供桌面端和移动端统一入口
- `database/mysql` 与 `docs/sql`
  - 数据库初始化脚本
- `scripts`
  - 启动与停止脚本

### 3.3 部署结构

系统运行时至少包含四类组件：

- Vue 前端应用，默认端口 `3000`
- Spring Boot 后端服务，默认端口 `8080`
- MySQL 8.0 数据库，默认端口 `3306`
- Redis 缓存，默认端口 `6379`

其中 Docker Compose 主要用于启动 MySQL 和 Redis，前后端通常分别由本地开发环境启动。前端通过 Vite 代理将 `/api` 请求转发到后端。

### 3.4 运行链路

典型请求链路如下：

1. 用户在前端页面发起操作
2. Axios 请求拦截器自动附带 JWT Token
3. Spring Security 过滤器解析 Token 并构建认证上下文
4. Controller 接收请求并调用 Service
5. Service 联合 Mapper、算法模块和数据库完成业务处理
6. 系统统一用 `Result` 包装响应
7. 前端根据响应结果更新页面状态、消息提示和路由跳转

## 4. 技术栈与技术选型

### 4.1 后端技术栈

- `Java 17`
  - 作为系统主要开发语言，兼顾性能、生态和工程稳定性
- `Spring Boot 3.1.10`
  - 负责自动配置、Web 服务、依赖集成与工程化启动
- `Spring Security`
  - 负责接口鉴权与角色权限控制
- `JWT`
  - 负责无状态登录凭证生成与解析
- `MyBatis-Plus`
  - 负责实体映射、CRUD、分页查询和 Lambda 条件构造
- `MySQL 8.0`
  - 负责持久化存储基础数据、教学任务、课表、调课记录等
- `Redis`
  - 主要用于登录退出时的 Token 黑名单控制，也具备缓存扩展能力
- `Knife4j / OpenAPI`
  - 提供接口文档能力，便于联调与测试
- `Lombok`、`Hutool`、`Guava`、`Fastjson2`
  - 作为常规开发辅助工具

### 4.2 前端技术栈

- `Vue 3`
  - 负责构建单页应用和响应式界面
- `Vite 5`
  - 负责开发服务器、代理、构建和分包优化
- `Vue Router 4`
  - 负责页面路由与访问控制
- `Pinia`
  - 负责用户信息、主题、布局等全局状态管理
- `Axios`
  - 负责统一请求封装、拦截器和错误处理
- `Naive UI`
  - 当前页面实现中使用最广泛的组件库
- `Element Plus`
  - 已作为依赖引入，但当前页面主要采用 Naive UI 组件
- `ECharts`
  - 已作为依赖引入，当前统计页以数据列表为主，后续可扩展图形化展示
- `Day.js`
  - 用于时间格式化与学期计算

### 4.3 算法与建模技术

- 自定义排课模型
  - `TaskData` 表示待排任务
  - `ClassroomData` 表示教室资源
  - `TimeSlot` 表示时间槽
  - `ScheduledTask` 表示排课结果
- 贪心算法
  - 适合快速生成可用课表
- 遗传算法
  - 适合在复杂约束条件下搜索更优解
- 冲突检测机制
  - 对教师、班级、教室三类冲突进行统一识别

### 4.4 技术选型理由

从论文角度，可以将技术选型理由概括为：

- Spring Boot + MyBatis-Plus 适合教学管理系统这种典型 CRUD + 业务编排型后台
- JWT + Spring Security 能以较低复杂度实现角色化访问控制
- Vue 3 + Vite 能兼顾开发效率和前端性能
- 将算法抽离成独立模块，有利于做算法对比实验和后续扩展
- Redis 黑名单方案适合无状态登录架构下的退出控制
- 多模块 Maven 结构有利于职责分离和论文中的模块化描述

## 5. 数据模型与数据库设计

### 5.1 数据库分层

数据库脚本体现出系统采用了“系统管理数据 + 教学基础数据 + 排课业务数据 + 约束数据 + 调课数据 + 同步数据”的分层建模思路。

### 5.2 核心实体

#### 5.2.1 用户与组织基础

- `sys_user`
  - 存储用户名、密码、角色、手机号、邮箱、状态、最近登录信息
- `sys_campus`
  - 存储校区信息和通勤时间
- `sys_department`
  - 存储院系组织结构

#### 5.2.2 教学基础数据

- `edu_class`
  - 存储班级、年级、学生人数
- `edu_teacher`
  - 存储教师工号、院系、职称、最大周学时、常驻校区
- `edu_student`
  - 存储学生与班级归属关系
- `edu_classroom`
  - 存储教室容量、类型、设备条件和状态
- `edu_course`
  - 存储课程名称、课程类型、学分、课时、实验要求、多媒体要求等

#### 5.2.3 排课核心业务数据

- `edu_teaching_task`
  - 作为排课输入源
  - 描述某学期某门课程由某教师为某班级授课的任务
  - 包含周学时、总周数、课程性质、优先级、固定时段、时间偏好等字段
- `sch_timetable`
  - 作为课表主表
  - 保存学期、版本、状态、算法配置、冲突数、利用率、满意度等汇总信息
- `sch_timetable_detail`
  - 作为课表明细表
  - 保存每一次课程安排的星期、节次、教师、班级、教室和冲突说明

#### 5.2.4 调课业务数据

- `adj_application`
  - 单门课程调课申请
- `adj_swap_application`
  - 两门课程交换申请

#### 5.2.5 约束与同步扩展数据

- `con_teacher_time`
  - 教师时间约束表
- `con_classroom_time`
  - 教室时间约束表
- `sync_config`
  - 外部系统同步配置
- `sync_log`
  - 数据同步日志

### 5.3 数据关系概述

核心业务对象关系可以概括为：

- 一个用户可以关联一个教师或学生身份
- 一个教师属于一个院系，并可关联常驻校区
- 一个班级属于一个院系
- 一门课程由某院系开设
- 一个教学任务关联一门课程、一个教师和一个班级
- 一个课表主表包含多条课表明细
- 一条课表明细来源于一条教学任务
- 调课申请和交换申请都围绕课表明细展开

### 5.4 设计特点

数据库设计体现出以下特点：

- 使用主从式课表结构，便于版本化管理
- 将“教学任务”和“排课结果”分离，符合排课系统的输入输出逻辑
- 预留了约束表和同步表，说明系统考虑过复杂约束和外部集成
- 调课采用申请单建模，便于流程跟踪和审计

## 6. 后端实现分析

### 6.1 分层组织

后端主应用模块采用常见的分层式组织结构：

- `controller`
  - 对外提供 REST 接口
- `service`
  - 定义业务服务接口
- `service.impl`
  - 具体实现业务逻辑
- `mapper`
  - 对应 MyBatis-Plus 数据访问层
- `entity`
  - 对应数据库实体
- `dto`
  - 用于请求和响应传输
- `config`
  - 安全、跨域、Redis、Swagger、异步线程池等配置
- `security`
  - JWT 鉴权过滤器
- `utils`
  - 当前用户解析等辅助工具

### 6.2 认证与权限控制

系统认证链路主要由以下组件组成：

- `AuthController`
  - 提供登录、退出、获取当前用户、重置密码、修改密码接口
- `UserServiceImpl`
  - 完成用户查询、密码校验、Token 生成、登录信息更新
- `JwtAuthenticationFilter`
  - 在每次请求中解析 Bearer Token
- `SecurityConfig`
  - 定义匿名接口、角色访问规则和无状态会话策略
- `RedisUtils`
  - 用于退出登录时写入 Token 黑名单

该方案的优点是结构清晰、无状态、实现成本低；不足是权限粒度仍主要基于角色，尚未扩展到菜单级或数据级权限控制。

### 6.3 业务控制器组织

后端控制器基本与业务域一一对应：

- `AuthController`
- `TeachingTaskController`
- `ScheduleController`
- `TimetableController`
- `AdjustmentController`
- `StatisticsController`
- `UserController`

这类组织方式适合论文中描述“面向业务域划分的接口层设计”。

### 6.4 统一异常与统一响应

系统通过 `Result` 和 `GlobalExceptionHandler` 实现统一响应封装与异常处理，具备以下工程价值：

- 前后端交互格式统一
- 业务异常与系统异常分离
- 参数校验、权限异常、资源不存在等错误有明确返回码
- 降低前端页面对后端错误场景的适配复杂度

### 6.5 异步任务处理

课表生成支持异步模式，关键实现包括：

- `AsyncConfig` 提供线程池 `taskExecutor`
- `TimetableGenerationJobServiceImpl` 使用 `ConcurrentHashMap` 维护任务状态
- 前端通过轮询查询任务状态

该设计能降低长耗时排课对前端体验的影响，但当前任务状态仅保存在内存中，服务重启后异步任务状态会丢失，这是后续可改进点。

## 8. 核心业务流程链路

### 8.1 登录流程

1. 用户在登录页输入用户名和密码
2. 前端调用 `/auth/login`
3. 后端根据用户名查询用户记录
4. 校验 BCrypt 密码和用户状态
5. 生成包含 `userId`、`username`、`role` 的 JWT
6. 返回 Token 和用户基础信息
7. 前端将 Token 存入本地存储和 Pinia
8. 后续请求由 Axios 拦截器自动附带 Token
9. 退出登录时，后端将 Token 写入 Redis 黑名单

这一流程体现了“无状态认证 + 黑名单注销”的实现方式。

### 8.2 教学任务管理流程

1. 管理员在教学任务页维护学期任务
2. 前端调用 `/task` 相关接口
3. 后端将任务写入 `edu_teaching_task`
4. 查询时支持按学期、状态、课程关键字筛选
5. 任务列表成为排课算法的直接输入数据源

教学任务是整个系统的“排课输入层”，也是业务流程的起点。

### 8.3 自动排课流程

1. 管理员在课表管理页选择学期和算法类型
2. 前端优先调用异步生成接口 `/timetable/generate-async`
3. 后端创建异步任务并记录任务状态
4. `TimetableService` 获取当前学期最新课表版本号
5. `ScheduleServiceImpl` 查询待排教学任务与可用教室
6. 系统按请求选择贪心算法或遗传算法
7. 算法输出 `SchedulingResult`
8. 若成功，则创建课表主表记录
9. 将排课结果逐条写入 `sch_timetable_detail`
10. 执行冲突重标记与冲突数修正
11. 前端轮询任务状态并在成功后跳转到课表详情页

这条链路体现了排课系统“任务输入 -> 算法求解 -> 结果落库 -> 冲突复核 -> 页面反馈”的完整闭环。

### 8.4 课表发布与生命周期管理流程

1. 新生成课表默认状态为 `DRAFT`
2. 管理员在课表详情页点击发布
3. 后端将课表状态更新为 `PUBLISHED`
4. 系统将相关教学任务状态更新为 `SCHEDULED`
5. 后续若不再使用可归档为 `ARCHIVED`
6. 已发布课表不能直接删除，必须先归档

这说明系统采用了明确的课表生命周期管理机制。

### 8.5 课表查询流程

1. 用户进入课表查询页
2. 系统按当前日期自动推算当前学期
3. 查询当前学期最新课表
4. 用户选择按班级、教师或教室查询
5. 后端从课表明细中筛选对应记录
6. 前端将结果渲染为周视图网格和课程列表

该流程实现了“面向对象维度”的课表访问方式，符合教学管理实际场景。

### 8.6 调课流程

1. 用户选择某条课表明细作为调课目标
2. 输入目标星期、目标节次和可选目标教室
3. 前端先调用 `/adjustment/check`
4. 后端构造目标排课预览对象
5. 在同一时间槽内检查教师、班级、教室冲突
6. 若无冲突，用户可提交申请
7. 系统保存 `adj_application`
8. 若课表已发布，则将任务状态置为 `ADJUSTING`
9. 用户确认执行后，系统更新课表明细
10. 对受影响时间槽重新计算冲突标记
11. 更新课表冲突总数
12. 若课表已发布，则任务状态变为 `COMPLETED`

### 8.7 课程交换流程

1. 用户输入同一课表中的两条课程明细 ID
2. 系统构造两门课程交换后的预览结果
3. 分别检查两门课程的新位置是否产生冲突
4. 若检测通过，可提交交换申请
5. 执行交换时，系统交换两条明细的时间和教室信息
6. 重新刷新受影响时间槽的冲突状态
7. 更新课表冲突总数和任务状态

### 8.8 统计分析流程

1. 用户在统计页选择课表
2. 前端调用 `/statistics/overview/{timetableId}`
3. 后端加载课表明细与可用教室
4. 计算总学时、课程数、教室利用率、教师工作量、冲突报告
5. 前端按标签页分类展示统计结果

统计模块的价值在于把排课结果从“静态明细”提升为“可分析数据”。

## 9. 排课算法设计分析

### 9.1 问题建模

系统将排课问题抽象为如下映射关系：

- 输入
  - 待排教学任务集合
  - 可用教室集合
  - 周工作日数和每日节次数
- 输出
  - 每个教学任务对应的一组 `时间槽 + 教室` 组合

其中：

- `TaskData` 描述课程名、教师、班级、周学时、优先级、课程类型、容量需求、校区偏好等
- `ClassroomData` 描述教室容量、类型、设备条件与所属校区
- `TimeSlot` 表示 `dayOfWeek + slotNo`

### 9.2 贪心算法思路

贪心算法实现逻辑可概括为：

1. 按任务优先级排序
2. 优先处理优先级更高、周学时更多的任务
3. 为每个任务寻找满足条件的教室集合
4. 遍历候选时间槽与候选教室
5. 过滤教师冲突、班级冲突、教室冲突
6. 使用评分函数选择当前最优解
7. 将结果写入已占用时间表中

当前贪心评分主要考虑：

- 上午前几节优先
- 周一至周四优先
- 教师常驻校区与教室校区匹配加分
- 教室容量与学生人数接近加分
- 同一门课多次上课尽量分散到不同日期

该算法优点是速度快、实现直观、适合快速得到一份可用课表；缺点是容易陷入局部最优，对复杂约束和全局最优不敏感。

### 9.3 遗传算法思路

遗传算法实现逻辑可概括为：

1. 根据任务集合随机初始化种群
2. 每条染色体由若干基因组成
3. 每个基因表示某个任务的一次授课安排
4. 通过冲突数和未完整排课任务数计算适应度
5. 在适应度基础上叠加软约束奖励
6. 采用锦标赛选择方式选择父代
7. 执行交叉生成子代
8. 通过时间槽变异、教室变异或联合变异提升搜索多样性
9. 保留精英个体并持续迭代
10. 达到目标适应度或最大代数后停止

当前适应度函数主要由以下部分构成：

- 冲突惩罚
- 未完整排课任务惩罚
- 上午优先奖励
- 周一至周四奖励
- 多次课程分散到不同日期奖励
- 完整排课比例奖励

遗传算法优点是更适合处理复杂组合优化问题，能在多次迭代中搜索更优解；缺点是实现更复杂，参数较多，计算成本更高。

### 9.4 约束设计

从当前代码看，真正参与排课决策的约束主要包括：

- 教师时间冲突约束
- 班级时间冲突约束
- 教室时间冲突约束
- 教室容量约束
- 教室类型与课程需求匹配约束

同时，系统还预留了但尚未完全接入求解过程的约束信息：

- 教师时间约束表
- 教室时间约束表
- 教学任务中的固定星期、固定节次、固定教室
- 教学任务中的时间偏好字段
- `ConstraintManager` 约束聚合器

因此，如果写论文，需要准确表述为：

- 系统已经实现了基于教师、班级、教室冲突和资源属性匹配的核心排课约束
- 对教师不可用时段、固定排课位置、复杂偏好约束等扩展能力，当前代码处于预留或部分接入状态

### 9.5 当前算法实现的技术特点

- 将算法从管理业务模块中独立出来，便于替换和对比
- 通过请求参数动态选择算法类型，具备策略切换能力
- 使用统一的 `SchedulingResult` 作为算法输出格式
- 将算法输出和数据库课表结构解耦，便于中间结果转换

## 10. 技术要点与实现难点

### 10.1 多约束组合优化难题

排课不是简单的 CRUD，而是一个 NP 难问题。系统的难点在于同时处理课程、教师、班级、教室和时间之间的多重约束。一旦任务规模增加，冲突组合数会快速上升。

### 10.2 算法速度与结果质量平衡

仅使用贪心算法，虽然速度快，但全局最优性较弱；仅使用遗传算法，则可能产生较高计算开销。系统同时保留两种算法，本质上是在“生成速度”和“解的质量”之间进行平衡。

### 10.3 课表结果的一致性维护

排课生成完成后，系统还需要保证：

- 主表统计值与明细表数据一致
- 课表冲突数量真实可信
- 发布后任务状态与课表状态联动
- 调课和交换后冲突信息实时刷新

因此，系统不仅要“算出结果”，还要“维护结果一致性”。

### 10.4 调课流程的业务复杂性

调课并不是简单更新一条记录，而是涉及：

- 冲突预检查
- 待处理申请识别
- 权限判断
- 执行后冲突重算
- 已发布课表下的任务状态联动
- 关闭其他相关待处理申请

这类操作体现了教学管理系统中“流程状态管理”的复杂性。

### 10.5 前后端异步协同

课表生成是长耗时任务。系统采用“后端异步执行 + 前端轮询”的方式处理，这解决了页面卡顿问题，但也带来了：

- 任务状态维护
- 页面轮询终止条件控制
- 成功、失败、超时场景反馈

### 10.6 多终端界面适配

系统前端不是简单的响应式缩放，而是桌面和移动两套布局逻辑。这样能提高可用性，但也会增加：

- 导航结构维护成本
- 页面交互一致性设计难度
- 布局状态管理复杂度

## 11. 系统亮点与论文可提炼点

如果将该系统作为毕业论文或课程设计的核心对象，可以重点提炼以下亮点：

- 采用多模块架构将管理业务、公共能力、排课算法和外部适配解耦
- 采用双算法方案，支持贪心算法与遗传算法对比
- 课表采用主表加明细表的版本化管理方式
- 支持异步生成课表，提高大任务场景下的交互体验
- 调课和课程交换不仅支持执行，也支持申请、取消和状态跟踪
- 统计模块可以从资源利用率、教师工作量和冲突分布多角度评估排课结果
- 前端支持桌面端与移动端自适应，提升系统可用性

这些内容都适合作为论文中的“系统特色”或“创新点描述”。

## 12. 当前实现的局限性与优化方向

### 12.1 约束能力尚未完全闭环

当前数据库中已经设计了教师时间约束表、教室时间约束表，教学任务中也预留了固定时段与时间偏好字段，但这些约束没有完全进入当前排课求解逻辑。后续可以将它们统一纳入算法适应度与可行性判定过程。

### 12.2 统计指标仍较简化

当前统计模块中：

- 总学时按“每条明细固定折算 2 学时”计算
- 教室总容量按固定 `5 天 * 10 节` 估算

该做法便于实现，但对真实教学场景的精确刻画还不够。后续可引入学时粒度配置、周次维度利用率和时段热力分析。

### 12.3 异步任务持久化不足

异步生成任务状态保存在内存中，服务重启会丢失。若系统面向真实生产环境，应考虑将任务状态持久化到 Redis 或数据库。

### 12.4 自动化测试缺失

当前各模块测试目录基本为空，这意味着：

- 排课算法正确性缺少自动回归验证
- 调课状态流转缺少边界测试
- 接口变更缺少集成测试保护

从论文角度，这也说明系统后续还可以补充“测试设计与验证”章节。

### 12.5 外部系统同步仍处于骨架状态

适配模块已经设计了同步接口、同步结果对象和针对不同教务系统的同步器骨架，但当前实现仍属于占位版本。后续可扩展为真实的主数据同步能力。

### 12.6 文档与实现存在轻微偏差

仓库中的 README 与当前实际代码存在少量不一致，例如组件库和部分版本信息已更新。这说明系统仍在迭代演进中，论文撰写应以源码真实实现为准。
